# HE Manager 跨平台桌面客户端实施方案

版本：1.0

日期：2026-10-17

目标平台：Windows 11 x64、macOS Apple Silicon（arm64）

状态：方案交付；客户端升级、双平台原型和性能验收尚未执行。

代码审阅基线：`kazalter/HE_manager@56935f06e8b032537ede50a7f62a7085030a8b7f`。

## 1. 项目决策

采用 **Vue 3 + TypeScript + Vite + Tailwind + Electron** 作为共用界面与桌面基础，复用现有 FastAPI 服务。视频与音频使用 libmpv，图片超分复用 Real-ESRGAN NCNN/Vulkan 资源；平台差异集中在桌面能力和媒体适配层。

优先级依次为：

1. 界面美观，浏览、阅读和播放体验完整。
2. Mac 与 Windows 共用主要界面、业务逻辑和开发流程。
3. 模块边界清晰，后续维护与迭代方便。
4. 主窗口内播放、可靠全屏、资源回收和性能可测。
5. 在满足以上要求后优化启动、常驻资源与安装体积。

本方案取代原计划中“Windows 原生控件优先、Mac 后置、暂停 Electron”的方向。保留原计划中有效的接口契约、媒体资源复用、任务取消、进度顺序和验收要求。

**Electron 是首选实施路线；双平台内嵌播放原型是技术可行性关卡。** 若原型证明需要承担不可接受的长期图形维护成本，先据证据调整选型，再开发完整播放器。不能把启动独立播放器窗口记为完成内嵌目标。

## 3. 技术选型与替代条件

| 层次 | 本期选择 | 选择理由 |
| --- | --- | --- |
| 共用界面 | Vue 3 + TypeScript + Vite + Tailwind | 复用现有代码、组件与前端知识，集中改善视觉和交互 |
| 桌面宿主 | Electron | 已有双平台基础；统一 Chromium 目标，复用现有桌面接口 |
| 服务端 | 现有 FastAPI 与数据库 | 沿用现有业务能力；本期不更换后端技术栈 |
| 播放引擎 | libmpv | 复用格式、字幕、音轨、硬解和着色器能力 |
| 图片增强 | 现有 Real-ESRGAN NCNN/Vulkan 引擎与模型 | 复用原生推理能力，补齐两端运行验证、队列与缓存 |
| 必要原生桥 | 小范围 C/C++ 绑定，macOS 必要处使用 Objective-C++ | 只承载图形、线程与资源互操作，不迁移业务逻辑 |
| 本地状态 | 现有配置与缓存文件；凭证使用 Electron safeStorage | 不为首版另建一套本地媒体业务数据库 |
| 分发 | Windows x64、macOS arm64 独立产物 | 共用源码，分别构建、装配运行资源和验证 |

Electron 的跨平台和原生扩展能力见[官方介绍][T1]。safeStorage 提供平台凭证保护能力，具体可用性与失败处理在两端验证，见[官方文档][T2]。

### 3.1 参考大厂的方式

借鉴“共用界面与业务、隔离平台能力、持续测量性能”的做法。VS Code 的官方架构明确区分通用、浏览器、Node 和 Electron 代码；Discord 在 2026 年 9 月仍公开升级桌面 Electron。[VS Code 架构][T3]、[Discord 更新][T4]。

这些案例用于说明路线可行，不作为 HE Manager 性能已经达标的证据。

### 3.2 Tauri 的位置

Tauri 2 是有条件的轻量化候选，本期不同时维护 Electron 与 Tauri 两套桌面宿主。

仅在现有客户端的启动、常驻资源或包体不符合明确目标时，开展一次同界面、同媒体资源的 Tauri 小原型比较。只有原型显示可复现改善，且两端播放器整合与维护成本可接受，才决定是否迁移。本期不同时建设两套完整客户端。

Tauri 使用系统 WebView，Windows 与 macOS 的网页引擎不同。它通常能省掉分发完整网页引擎的成本，但不能据此推导滚动、播放或推理一定更快。[Tauri 进程模型][T5]。

默认视频与图片以原画显示，增强由用户主动启用。图片增强处理中保持原图可读；失败或取消后仍可继续浏览。

视频/漫画使用现有服务端进度。音频曲目与时间首版保存在本机，并按服务器、账号、作品隔离；不承诺音频逐曲进度跨设备同步。

## 5. 视觉与交互设计

### 5.1 视觉方向

使用统一的 HE Manager 产品风格：封面和内容为主，侧边导航清楚，信息密度适中，操作反馈及时。系统标题栏、窗口按钮和快捷键保留平台习惯。

CP-02 先实现三个真实可运行场景：

1. **媒体库**：侧栏、搜索与筛选、继续观看、封面卡片、长标题、收藏与进度。
2. **播放器**：视频区域、控制条、音轨/字幕菜单、增强设置、缓冲与失败状态。
3. **阅读器**：单页/双页/卷轴、页码、缩放、增强排队与进度提示。

每个场景都用真实长标题、横竖封面、缺失封面和空结果验证，不只使用理想样例。

### 5.2 共享设计规则

- 统一字体层级、间距、圆角、强调色、图标与交互状态，集中在主题变量和基础组件中。
- 初始采用 4/8 像素间距体系，正文约 14～16 CSS 像素，主要操作具备清晰的可点击区域；具体值在 CP-02 的两端实图中收敛。
- 浅色、深色和跟随系统同时完成；正文、辅助文字和焦点提示在两种主题下都可辨认。
- 共用 Button、Menu、Dialog、Slider、Toast、MediaCard、EmptyState、LoadingState 等基础组件；优先整理现有组件。
- 不因样式需求再引入另一套前端框架，也不并用多个覆盖相同职责的整套组件库。
- 列表、图片和阅读页采用渐进加载；动效要允许降低，不阻塞输入或掩盖加载状态。

### 5.3 视觉验收

在 Windows 与 Mac 上分别检查约 1280×800 的代表窗口及 1024×640 的初始最小内容区设计。分辨率以逻辑尺寸为准，最小窗口值根据实际内容在 CP-02 锁定。

同一组件在两端保持相同的产品层级与交互含义；字体渲染、窗口按钮位置和系统菜单允许体现平台差异。截图检查与键盘、鼠标、触控板操作都要进行，不能只验设计稿。

## 6. 模块边界与代码复用

沿用现有目录，按职责整理，不以大规模搬目录或全量改写语言作为前置工作。

| 模块 | 主要职责 | 明确边界 |
| --- | --- | --- |
| frontend 页面与组件 | 媒体库、查看器、阅读器、设置、主题 | 不直接处理原生指针、进程启动和 DLL 路径 |
| frontend 通用业务 | 查询、分页、媒体模型、查看状态、进度意图 | 不混入平台图形逻辑 |
| 桌面能力契约 | 延续 heDesktop，补类型、错误与事件约定 | 页面使用统一能力，不到处判断平台 |
| desktop 主进程服务 | 生命周期、菜单、窗口、鉴权代理、配置、任务调度 | 不承载 Vue 布局，不同步执行耗时推理 |
| PlayerSession | 播放命令、状态、事件、媒体归属和释放 | 界面不依赖播放器所在进程或纹理格式 |
| ImageEnhancementService | 输入下载、任务、引擎、结果缓存与取消 | 不直接修改当前页面，结果携带请求归属 |
| 原生媒体适配 | Windows/Mac 渲染出口、纹理互通、必要硬解配置 | 不放收藏、筛选、评分等业务 |
| resources / scripts | 平台运行库、模型、着色器、锁文件、打包 | 不依赖开发机上的临时绝对路径 |

已有主进程 .cjs 代码可以渐进整理。新增接口和共享模型优先使用 TypeScript；全量将 .cjs 改为 .ts 不作为首版完成条件。

继续维护一套正式客户端实现。网页入口可复用通用界面与 API；桌面能力通过适配层启用，不把 Electron 模块导入浏览器通用代码。

## 7. 第一技术关卡：双平台内嵌 libmpv

### 7.1 固定目标

视频必须进入 HE Manager 主窗口的显示区域；Vue 控制条、菜单和界面状态能够正常覆盖、点击和获得焦点。全屏保留同一播放会话。

旧版独立 mpv 窗口可以在迁移期作为显式兼容入口保留，不能作为 CP-01 或首版内嵌验收通过的依据。

### 7.2 首选原型路线

验证“libmpv 原生渲染 → 平台共享纹理 → Electron 页面内视频区域”的路线。

Electron 的 sharedTexture 能导入平台纹理为 VideoFrame；Windows 使用 NT HANDLE，macOS 使用 IOSurface 类型。相关接口目前标记 Experimental，因此需要锁定版本、验证释放规则并评估升级维护成本。[共享纹理接口][T6]、[平台纹理类型][T7]。

首个原型使用薄 native addon 与专用原生渲染线程，减少初期跨进程变量。耗时原生工作不能同步阻塞 Electron 主线程。采用 C/C++ 只是这一小层互操作的实现选择，不将应用业务迁移过去。

CP-01 结束时锁定以下决策：

| 决策 | 必须形成的结果 |
| --- | --- |
| Windows 渲染出口 | libmpv 版本、实际 renderer/VO、图形后端、可导入纹理格式与同步方式 |
| macOS 渲染出口 | 原生 arm64 运行库、实际渲染与纹理互通方式、Retina 尺寸处理 |
| 播放进程位置 | 选择主进程加载 addon + 原生线程，或专用 helper；正式版只维护一种 |
| 帧与引用管理 | 有界在途队列、消费者变慢时的处理、引用释放和关闭时限 |
| 兼容结果 | 两端的实际硬解、Anime4K 模式、字幕、定位、全屏和资源情况 |
| 构建可复现性 | 来源 commit/版本、工具链、构建命令、二进制哈希、依赖 |

native addon 是绑定形式，helper 是进程位置，两者不互斥。若选择 helper，增加进程隔离的同时必须实现平台资源转移；不能把属于另一个进程的纹理整数地址当作有效跨进程句柄。

不预先承诺全链路零拷贝。要求避免“每帧读回 CPU，再把整帧像素通过普通 JS IPC 发送”的默认方案；实际复制、同步和合成成本由原型测量。

### 7.3 mpv 版本边界

截至本方案日期，mpv 新 D3D11 Render API 位于 0.42.0 开发线、client API 2.6，不能假定稳定版 0.41.0 已有该接口。若 Windows 原型采用它，需要锁定具体源码构建、匹配头文件和依赖。[API 变更记录][T8]、[D3D11 定义][T9]。

该版 Render API 使用 gl_video 渲染实现，与原有 gpu-next 路径不同。旧 Anime4K 自检不能直接作为新路径的画质或性能结论；Mac 同样要独立验证。[Render API 后端][T10]。

原 WinUI 的 SwapChainPanel 绑定方案不作为本方案的跨平台媒体出口。CP-01 可以比较可行的稳定接口，但只选一条正式实现，不能将 Windows 上已显示视频推定为 Mac 也已可用。

### 7.4 CP-01 通过条件

1. 两个平台均以打包后的最小程序，在主窗口中显示真实视频。
2. 本地代表片与真实受保护服务器流都能播放；HTTP 拖动正常。
3. DOM 控制条和弹出菜单能覆盖视频并接收输入；调整窗口尺寸不破坏显示区域。
4. 两端分别记录实际硬解，并验证 Anime4K 的原画/效率/质量配置变化；不以按钮变化代替着色器运行证据。
5. 普通进入/退出全屏不重新 loadfile，保持进度、暂停状态、字幕、音轨和倍速。
6. 切换影片、关闭查看器、最小化恢复和退出后，没有黑屏挂起、释放后回调或未受控增长的资源。
7. 提供两端最小可运行包，验证不依赖开发环境中的隐式动态库。

CP-01 的通过结果必须对应最终选定的进程位置、渲染出口和纹理传递方式。若主进程原型通过后改为 helper，或更换了渲染及跨进程纹理方案，须用该形态重新执行受影响平台的上述验收；两端最终选定形态均通过后，才能关闭此关卡。由此增加的工作单独评估，不默认包含在 3～5 日探索预算内。

CP-01 使用少量代表内容确认可行性。完整格式矩阵、长时播放和压力验收放在 CP-04/CP-06，不能在原型阶段就把它们标为已通过。

### 7.5 线程与释放规则

同一 render context 的调用串行执行，更新回调只发调度信号。控制/事件、渲染、纹理导入和页面消费的线程职责必须明确；渲染路径不等待可能造成 mpv core 死锁的同步命令。

源纹理必须保持有效，直到所有消费者引用真正释放，不能凭“发送完成”就销毁或复用。停止会话先阻止新工作，清理在途回调与纹理引用；render context 必须先于 mpv core 释放。退出不无限阻塞 UI。[libmpv 线程与生命周期][T11]、[Electron 引用释放规则][T6]。

### 7.6 失败分支

CP-01 使用 3～5 个有效开发日作为初始探索预算。到期必须产出可复现的通过结果，或明确失败位置、尝试路径、继续投入和维护成本；这不是保证五天解决所有图形问题。

若任何一端无法可靠完成嵌入、覆盖或释放，先定位问题。若结论是必须承担大量长期私有图形补丁，再针对该阻塞比较一个候选，例如 Flutter + media_kit；重新评估 UI 重写成本、其播放器版本、Anime4K 与两端资源管理，不自动切换或同时建设多套客户端。[media_kit 项目][T12]。

若问题仅是包体或常驻开销，按第 3.2 节比较 Tauri。外部播放器可用不抵消内嵌关卡失败。

## 8. 播放会话与窗口行为

采用应用级 PlayerSession；首版同时只有一个活动视频或音频会话。

| 操作 | 行为 |
| --- | --- |
| 音频播放时浏览媒体库 | 保留音频与底部播放条 |
| 打开视频 | 保存旧音频位置并停止旧会话，进入视频 |
| 开始音频作品 | 结束当前视频或旧音频，打开选定曲目 |
| 关闭视频查看器 | 保存进度，停止视频并释放对应资源 |
| 进入/退出全屏 | 保留同一媒体会话，只调整宿主窗口和显示区域 |
| 最小化 | 默认保持播放会话；避免无意义的页面刷新和帧队列积压 |
| 关闭主窗口 | 停止当前媒体与无使用者的增强任务；Mac 可保留无窗口进程供 Dock 重开 |
| 退出应用 | 最终保存采用有界等待；释放播放器、任务和资源后退出 |
| 退出账号/切服务器 | 结束旧身份会话，取消待发送请求，隔离旧状态和缓存 |

Mac 的全屏转换是异步的，以 enter-full-screen / leave-full-screen 事件更新状态；不能调用设置函数后立即假定已经完成。正常全屏保持同一 mpv 实例和媒体，允许调整交换链/纹理等显示资源；设备丢失等异常允许必要恢复。[Electron 全屏文档][T13]。

Esc 优先关闭当前弹层，其次退出全屏，再关闭查看器；不会在输入框正常编辑时误触播放快捷键。窗口退出全屏后恢复合理的位置和尺寸，断开显示器后保证窗口仍在可见区域。

视频/音频前后项沿用用户打开时的列表或曲目顺序；列表变化不悄悄重排当前会话队列。跨分页下一项复用分页加载，不能要求先拉全库。

## 9. API 与客户端状态契约

以下接口事实来自审阅基线。新增的客户端处理规则属于本方案设计；默认不要求服务端增加接口或迁移数据库。

| 业务 | 现有契约 | 客户端实现规则 |
| --- | --- | --- |
| 登录 | GET /auth/status；POST /auth/login；GET /auth/me；POST /auth/logout | token 是不透明字符串，不解析 JWT，不构造不存在的 refresh 接口 |
| 媒体列表 | GET /media 返回数组；总数来自 X-Total-Count；limit 上限 200 | 初始页大小 60，按 offset 获取；搜索/筛选变更重置页并丢弃旧响应 |
| 排序/筛选 | sort=date/title/rating/opened；tag 为名称；source_site=local 对应本地来源 | UI 选项明确映射到真实字段；继续观看使用 viewing + opened |
| 真正打开 | GET /media/{id} 会更新 last_opened_at，并可能将 unviewed 改为 viewing | 只在用户真正进入查看/播放时调用，封面预取与卡片悬停不调用 |
| 视频/独立图片 | GET /stream/{id}；保留 200/206、Range、Content-Range、416 | 视频交媒体引擎；image 类型交图片查看器；416 不当作登录失效 |
| 漫画信息 | GET /manga/{id}/pages?include_dimensions=true；total_pages、page_dimensions | 尺寸形状为 [[w,h],null,...]，也可能为空；缺尺寸用占位回退 |
| 漫画页 | GET /manga/{id}/page/{page_index}，索引从 0 开始 | 所有下载显式 track_progress=false；实际显示事件单独驱动进度 |
| 收藏/评分 | PATCH /media/{id}；favorite 布尔、rating 0～5 | 只提交修改字段，避免旧 DTO 顺带覆盖新进度 |
| 视频进度 | 整数秒 progress/duration；有效时长下达到 95% 为 viewed；0 为 unviewed | 恢复 seek 完成前不保存瞬时 0；时长有效时同步 duration |
| 音频作品 | GET /audio/{id}/tracks → tracks 数组 | 单文件与目录作品统一转换为曲目列表 |
| 音频曲目 | GET /audio/{id}/track/{position}，按 tracks[position-1] 取曲目 | 使用列表位置 1～N，不能假设 manifest index 连续 |
| 音频恢复 | 现有媒体 progress 没有完整逐曲位置语义 | 本地保存 position/time，按服务器+账号+作品隔离 |
| 标签/封面 | GET /tags；cover_path 可空，对应 /thumbnails 路径 | 空封面有正常占位；不把服务器绝对路径当成本机路径 |

独立图片分类使用 media_type=image 和 /stream；漫画分类使用 media_type=manga 和漫画页接口。漫画作品里的页面不假定为独立图片条目。

依据：[媒体类型][R6]、[媒体路由][R7]、[音频路由][R8]、[鉴权][R9]、[Schema][R10]、[漫画尺寸服务][R11]。

### 9.1 鉴权与资源读取

Electron 主进程负责保存和使用桌面 token，前端使用受控 API/资源访问接口。延续现有 he 协议/代理边界，覆盖封面、独立图片、漫画和普通 API；libmpv 自己发 HTTP 时单独配置 Bearer 头，不能指望自动继承应用 HTTP 客户端的配置。

token 不进入进程参数、日志或可复制资源 URL。保持 contextIsolation、受控 preload 和窄化 IPC；页面不获得任意文件、进程和原生句柄能力。

首次打开作品完成身份与详情验证；缓存仅在当前有效授权会话内使用。401 后停止旧身份请求与显示，进入重新登录；断网显示连接问题。首版不以缓存实现离线打开新作品。

正常关闭应用保留可恢复登录状态；主动退出账号尽力调用 logout，即使离线也完成本地退出。

### 9.2 请求与写入顺序

请求创建时固定 serverKey、userId、authGeneration、mediaId、sessionGeneration；回调只有仍属于当前会话时才能更新 UI。

进度写入的互斥键使用 serverKey + mediaId，与服务端共享媒体状态一致；每条意图仍携带 userId + authGeneration + sessionGeneration，用于身份校验、淘汰和结果归属。同一互斥键最多一条在途请求；切换账号后丢弃未发送的旧意图，但不得另建并行写入器绕过旧在途请求。

尚未发送的普通进度合并为最新意图；视频约 5 秒节流，在暂停、结束、切换与正常退出时补交最终位置。

切换媒体前捕获旧会话的位置，交给旧媒体写入器；回调不得再读取已经改变的 currentMedia.id。同一媒体重开时沿用该写入器的顺序约束。

UI 取消请求不等于撤销已到达服务端的写入。登录/服务器切换后丢弃未发送旧意图；已发送请求保留原身份和媒体归属。恢复网络后只重试仍有效的最新意图，不补发一串历史进度。

以上尽量约束本客户端的发送顺序；请求超时后，服务端是否已经提交不能确认。现有服务端没有进度版本号/CAS，跨设备同时操作仍可能最后写入覆盖；首版沿用服务端共享媒体进度，不承诺严格的全局写入顺序、每用户独立进度或多设备冲突合并。

### 9.3 漫画可见页与第 0 页

进度由 VisiblePageChanged 驱动：图片属于当前会话、成功显示并进入阅读区域后触发。网络下载和缓存命中使用同一条路径；预加载不触发。

阅读锚点：单页使用当前页；双页使用已显示的最大服务器页码；卷轴使用视口中部阅读线对应页，抵达文档底部时提交最后一页。RTL 改变布局和翻页方向，不改服务器索引。

现有服务端把多页漫画的 PATCH progress=0 设为 unviewed。首版兼容规则：

1. page_index > 0：PATCH progress，采用返回状态。
2. 多页漫画第 0 页：先 PATCH {progress:0}，再 PATCH {view_status:"viewing"}。封装成同一逻辑写入，两步之间不插入其他进度写入。
3. 单页漫画：只 PATCH {progress:0}，保留服务端对唯一末页的 viewed 结果。
4. 两步不是服务端事务。第二步失败时，只在它仍是最新阅读意图时重试；已翻到别页则提交最新意图，不让旧 viewing 覆盖末页状态。

可以另行做一个无数据库迁移的兼容修正，让服务端仅在“多页漫画 + progress=0 + 显式 viewing”时尊重 viewing；此改动是可选优化，在部署与验证前不能假定合并请求已经有效。

## 10. 图片、阅读缓存与 GPU 任务

### 10.1 任务策略

同一时刻最多一个图片推理任务。当前可见图片/跨页优先，相邻页预处理有界。翻走后取消未使用的排队任务；运行中的任务若已无使用者则终止并清理。多个使用者共用同一任务时，单个取消不影响其他使用者。

状态至少包含：排队、运行、完成、取消、失败、超时、格式/尺寸不适用。结果必须带会话和内容标识；原图始终可读，迟到结果不能覆盖新页面。

视频启动后暂停新后台图片推理，取消无使用者的旧任务并等待资源清理；无需为首版建设通用 GPU 调度框架。

### 10.2 三种资源预算

| 资源 | 控制办法 |
| --- | --- |
| 磁盘结果缓存 | 默认约 1 GiB，设置中可调整；原图/缩略图/增强结果计量清楚，原子写入、淘汰旧结果 |
| 已解码图片内存 | 按像素字节预算与可见范围释放，不用“缓存文件只有几 MB”推测内存；数值由 CP-05 实测锁定 |
| GPU/推理资源 | 推理并发为 1，限制输出像素与 tile；关闭和取消后验证释放，不与播放任务无限竞争 |

1000×1400 的图片做 4× 后是 4000×5600。一份四字节 RGBA 缓冲约 89.6 MB，双页约 179.2 MB，尚未包含原图、纹理与推理中间结果。这是尺寸计算，用于预算，不是实际峰值测试。

沿用现有 tile、输出像素限制和模型配置作为起点，再分别在 Windows 与 Mac 上测量。超过预算时给出原因并保留原图，不盲目启动推理。

### 10.3 缓存键与内容变化

缓存键包含服务器、账号、媒体/页面标识、内容指纹或版本、引擎版本、模型和参数。账号隔离、原子写入和失败清理必须落实。

缓存命中不跳过当前身份验证或实际显示事件。若响应提供可靠的内容版本或验证器，可使用条件请求校验；当前漫画接口没有可依赖的页面内容版本，首版采用以下规则：每次新阅读会话，页面首次需要显示或处理时，经鉴权并绕过客户端 HTTP 缓存获取原图字节，计算内容哈希，再以该哈希查询持久化增强结果缓存。同一阅读会话内复用已取得的字节、哈希和处理结果；重新打开作品或用户主动刷新时重新取图校验。无可靠版本的独立图片采用同样规则，首版不要求新增接口。

因此，增强缓存命中可以省去推理，但在当前接口条件下，不承诺跨会话省掉原图验证下载。缓存命中后的漫画页仍进入 VisiblePageChanged 路径，不改变第 9.3 节的进度规则。

先测量下载、排队、进程/模型启动、推理、结果编码和显示耗时。只有重复模型加载被证实为主要瓶颈时，再考虑常驻推理进程；首版不强制重写现有推理框架。

CP-05 的两端都须至少完成一张动漫 2× 和通用图片 4× 代表样例。整个 Mac 引擎不可用不能以“支持原图回退”记为图片增强验收通过。

## 11. 双平台开发、构建与分发

### 11.1 开发方式

同一仓库维护正式代码；遵循现有仓库协作规则。Mac 和 Windows 工作副本都可以开发通用代码，通过 Git 交换同一版本，不以手动复制文件同步。

通用前端与核心逻辑在两端均可运行和测试。原生模块和分发产物分别用目标平台工具链构建；同一提交分别产出 Windows x64 与 macOS arm64 包。需要生产服务器集成时使用受控测试数据，不以重写客户端为由变更媒体原文件。

### 11.2 版本与资源

在 CP-01 选择经验证的稳定 Electron 版本并锁定；原生 addon、libmpv、推理引擎、模型与着色器记录来源、版本/commit、架构和 SHA-256。若必须使用开发版 mpv，单独标明原因、固定构建和回归范围。

沿用按平台分离的 runtime 目录。包内包含运行所需资源，普通用户无需另装 Node、Python、编译器或 CUDA 工具包；是否依赖系统图形驱动由能力检测和运行说明明确。

签名、公证与安装方式按实际分发范围落实。CP-01 先完成最小可运行包；CP-07 再完成正式体验包、完整说明和目标环境安装验证。公开分发时另配置所需签名/公证凭证与发布流程。

### 11.3 构建与验证边界

CI 负责前端构建、接口/状态测试、原生模块构建和包内依赖检查。GPU、全屏、输入、画质和功耗必须在两台目标真机验证，不能以 CI 构建成功代替。

每次阶段交付记录：源码 commit、构建命令、工具与依赖版本、产物哈希、两端通过项、未通过项和复现步骤。

## 13. 性能基线与测试矩阵

### 13.1 性能记录

同一台机器上比较旧版与新版；两台机器分别建立自己的基线，不直接以 Windows 数字衡量 Mac 是否合格。

固定服务器、网络条件、内容集、输出分辨率与操作流程，记录：

- 冷启动至可操作页面。
- 固定媒体规模下首屏、搜索、滚动和返回位置。
- 全应用相关进程的内存/CPU，以及 GPU 资源；不只统计主进程。
- 缓存命中/未命中的翻页延迟，原图与增强结果分别记录。
- 增强任务的下载、排队、启动、推理与显示分段耗时。
- 视频 renderer、实际硬解、源/输出尺寸、着色器模式、帧时间和掉帧。

具体启动、内存和交互阈值在 CP-00/CP-01/CP-03 有基线后锁定。验收表不得长期留空，但本方案不编造尚未测得的“100 ms”或“降低 50%”。

### 13.2 最终真机矩阵

| 组别 | 两端执行内容 |
| --- | --- |
| 主流程 | 登录→筛选→查看→保存位置→返回→重开；切账号与切服务器 |
| 视频 | H.264/HEVC/AV1 的 MP4/MKV 代表样例；1080p24、1080p60、4K24 分开记录；字幕、音轨、倍速、HTTP 跳转 |
| 增强 | Anime4K 关闭/效率/质量；动漫图片 2×、通用图片 4×；不适用尺寸和失败回退 |
| 阅读 | 单图、单页漫画、双页、RTL、卷轴、缓存命中、第 0 页、末页、损坏图片与缺失尺寸 |
| 资源 | 20 次全屏往返、50 次切片、50 次快速翻页/切档；记录回收后的趋势 |
| 网络 | 断网、慢请求、401、服务重启、416、取消后迟到结果 |
| 窗口 | Windows 100%/125%/150%/200% 缩放；Mac Retina 与触控板；焦点、最小化、多显示器、全屏恢复 |
| 分发 | 两端不安装开发工具的目标运行环境，启动和完整主流程 |

30 分钟视频掉帧比例低于 0.1% 可作为代表配置的初始目标。须先固定计数器、统计分母、开始/结束区间和排除的起播/跳转片段；没有可靠计数器时记为“不可用”，不能记为零。目标不适用于未经验证的任意片源/增强组合，超出目标时查明原因并调整默认档位或支持范围。

合成片用于证明链路，真实日常内容用于画质与持续体验检查。功耗和温度只在可获得可靠数据时报告。

## 14. 测试分工与完成标准

### 14.1 有价值的自动测试

- API 响应形状、分页总数、媒体类型和空字段。
- 第 0 页与末页进度、未知时长、音频曲目位置。
- 旧请求/旧会话不改新页面，串行写入器不会反向覆盖。
- 图片队列上限、共享任务取消、缓存隔离和迟到结果。
- 包内资源路径与缺失依赖处理。

视觉细节采用实际页面和截图审阅。原生纹理、硬解、全屏与设备恢复结合小型集成测试和真机操作，不写只复述实现的测试充数。

### 14.2 首版完成标准

1. Windows x64 与 macOS arm64 都有可运行分发包。
2. 两端基础浏览、图片/漫画、视频/音频流程完整，没有占位页面。
3. 视频真实内嵌，控制条和菜单覆盖正常，全屏保留会话。
4. 两端的媒体与增强能力经过代表内容验证，已知限制明确。
5. 账号、缓存、请求和观看进度不会在客户端串到错误媒体或身份。
6. 快速切换、取消、重复全屏和长时播放后资源可回收。
7. 视觉基线已落实，主题、窗口与平台输入通过。
8. 构建、自动测试、真机结果分别记录；未验证事项不写为通过。

## 15. 主要风险与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| Electron 纹理接口仍为实验性 | 升级兼容与释放逻辑需要维护 | 固定版本，CP-01 验证后锁定路径，升级触发媒体回归 |
| 新 mpv API 与旧渲染器不同 | Anime4K 效果/性能不能直接继承 | 记录具体 renderer 与 API，重新比较代表样例 |
| Mac 运行库/推理引擎缺口 | UI 能跑但媒体增强不可用 | 前期检查 arm64 资源，CP-05 两端实际完成增强 |
| 多页漫画第 0 页状态差异 | 阅读后被标为未读 | 采用两步兼容写入；可选最小后端修正独立验证 |
| 图片缓冲与推理占用过大 | 快翻卡顿、内存增长、影响视频 | 分开磁盘/RAM/GPU 预算，限制并发与在途工作 |
| 两端测试后置 | 平台差异累积返工 | 每阶段都在两端执行代表操作 |
| 范围扩大 | 首版迟迟无法形成 | 首版范围固定，新增业务进入后续清单 |

## 16. 开工顺序

1. 对照本方案记录现版两端基线、资源与目标系统。
2. 在现有 Electron 工程中完成最小双平台内嵌原型和运行包。
3. 同步形成三个代表界面的共享视觉规则。
4. 原型通过后，按媒体库→视频音频→图片漫画的顺序接入完整业务。
5. 做平台交互与性能收敛，产出两端正式体验包。

本次交付到方案为止。后续实施以阶段产物和验收证据推进，不把文档完成、工程能编译或单个平台能启动当成客户端已经交付。
